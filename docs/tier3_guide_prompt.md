## 一、流程纪律 — "不跳步"

> 教训来源: AAPL 2.8/5 — 跳过Phase -1/-0.5，66K字符，系列最差

**R1. 永远从脚本启动，不从记忆启动**
- 第一条命令必须是 `bash scripts/tier3_launch.sh {TICKER} {INDUSTRY}`
- 然后是 Phase -0.5 文献侦察 → `bash scripts/preflight_gate.sh` → 必须 CLEARED
- 即使用户说"快速开始"或"直接分析"，也不得跳过。宁可多花15分钟准备，也不接受66K的灾难

**R2. 单会话禁跨Phase**
- 每个Phase结束时运行 `bash scripts/phase_complete.sh`，它包含Circuit Breaker
- 如果Sentinel返回BLOCK，**停下来修复，不要强行继续**
- 过去的教训: 单会话急速完成 = 质量灾难。AB-003抗体会检测这个

**R3. 阅读launch_brief再动手**
- launch_brief.md包含目标字符范围、参考报告、进化教训
- 如果目标是300K，你的产出不应低于150K (50%下限)
- 如果偏离目标超过50%而不停下来审视，你在犯AAPL同样的错误

## 二、数据诚信 — "不编造"

> 教训来源: RBLX 3.6/5 — 单源SBC数据($2.65B)传播240+处，APIC硬约束本可即时否决

**R4. 每个关键财务数字至少两源交叉验证**
- FMP数据≠真理。FMP的SBC字段经常返回$0
- 关键数据(收入/利润/FCF/SBC/CapEx)必须: MCP工具 + WebSearch 或 10-K原文对比
- 如果两源差异>10%，必须在DM中标注差异并说明采用逻辑

**R5. 无源数字禁写**
- 报告中每个数字必须有DM锚点 [DM-XXX-NNN] 或明确的外部来源或公式推导
- 不得凭记忆写财务数字。"我记得苹果的毛利率大约是..."——不行，去查
- P0阶段的数据错误会在每个Phase放大10倍(RBLX教训)

**R6. DM锚点必须全局唯一**
- 如果使用并行Agent，预先分配前缀: A用DM-BIZ/DM-TECH, B用DM-RISK/DM-GEO, C用DM-FIN/DM-VAL
- 组装后去重会导致锚点数量下降(AMAT教训: 625→106)

## 三、算术与估值 — "不假装精确"

> 教训来源: MSFT 3.5/5 — WACC±100bps跨越3个评级区间；FCFF表内部矛盾+敏感性矩阵8/9格错误

**R7. LLM不能做算术，DCF必须Python验证**
- 所有FCFF推导、敏感性矩阵、WACC计算必须用 `tests/verify_dcf_arithmetic.py` 验证
- 不得手动心算DCF然后写入报告。你会算错。你每次都会算错
- 敏感性矩阵: 必须是公式推导，不得手工填数

**R8. Reverse DCF优先于正向DCF**
- 先问"市场在赌什么"(反推隐含增长率/利润率)，再评估这些假设是否合理
- 正向DCF ("这家公司值XXX") 是估值的第二步，不是第一步
- KLAC教训(4.5/5): 信念反演发现TAM不可能性证明 = 全系列最强洞见

**R9. 方法独立性审计**
- 如果你用了5种估值方法，检查它们是否真的独立
- AMAT教训: 5方法中3个共享核心假设(增长率+利润率) = 实际2.5方法
- AB-006抗体会检测: 任何两种方法结果差<3% → 假独立
- 如果方法间离散度<1.5x，你在用不同名字做同一件事

**R10. 不给假精度**
- WACC±100bps跨越3个评级区间(MSFT) → 不要把目标价精确到个位
- 市值>$500B的巨头: 从"值多少钱"转向"什么条件下变便宜/变贵"
- 置信度要诚实: 如果真实置信度是40%，不要写60%

## 四、分析深度 — "密度>体量"

> 教训来源: KLAC 4.5/5 (254K) > APP 4.1/5 (452K) — 更短的报告更好

**R11. 一个杀手级洞见 > 十个泛泛分析**
- APP最好的部分: 客户漏斗重建(6400→60) — 用第一性原理拆解管理层叙事
- KLAC最好的部分: TAM不可能性证明 — 信念反演发现市场隐含假设自相矛盾
- GOOGL最好的部分: 三面承重墙分析 — 最少几个信念失败即改变评级
- 问自己: 这份报告的"杀手级洞见"是什么? 如果没有，你在写流水账

**R12. 写一次写对，不要补丁**
- KLAC教训: v1.0无补丁 > v1.x多轮修正。缝合痕迹破坏可读性
- 在Phase 1-3写的时候就要写对，而不是指望Phase 4红队来修
- 如果Phase 4大幅下调了Phase 1-3的内容，说明前序Phase质量不够

**R13. 承认能力边界**
- 管理层质量评估: AI判断力有限 → 标注"诚实区"，不强行评分
- Pre-revenue业务(Reality Labs/EPIC Center): 数据不足 → 用期权树或条件估值，不过度加权
- 二元事件(反垄断拆分): 不适合连续估值模型 → 用条件估值(拆分前/后)

## 五、红队与偏差 — "有效挑战>表演性挑战"

> 教训来源: MSFT — 41K字符红队净效果0pp=纯表演；AMAT — Phase 4全部8CQ下调无一上调=系统性悲观

**R14. 红队5K有效 > 50K表演**
- 有效红队: 找到一个能改变评级的论点
- 表演红队: 列举20个"需要关注"但不改变任何结论的点
- 每条红队挑战必须有明确的"如果我说对了，评级如何改变"

**R15. 双向校准: 不只挑战乐观，也检查过度悲观**
- AMAT教训: P4对8个CQ全部下调，无一上调 = 系统性悲观偏差
- 红队后检查: 有没有我过度悲观的维度? 有没有我低估了正面催化剂?
- 概率调整应该是双向的: 有些CQ应该上调

**R16. 承重墙脆弱度测试**
- 识别论文的3-5面"承重墙"(核心假设)
- 对每面墙测试: 如果这面墙倒塌，整个论文还成立吗?
- GOOGL教训: "三面承重墙"分析 = 最有效的风险评估方法

## 六、合规与呈现 — "一次性文档感"

> 教训来源: 组装检查清单 — Agent引用=0, Phase标题=0, 市值一致

**R17. 地缘政治中性表述**
- 禁止: "中国入侵台湾" / "invasion of Taiwan"
- 使用: "台海冲突" / "台海危机" / "cross-strait tension"
- Polymarket引号内原文例外，描述性文本必须中性

**R18. Complete报告必须像一次性撰写的连贯文档**
- Agent引用残留 = 0 (CG15会检测)
- Phase标题残留 = 0
- 市值基准全文唯一 (CG16会检测)
- P/E等估值指标全文一致 (CG17会检测)

**R19. 交叉验证声明≥3次**
- 报告正文必须出现至少3次"交叉验证"相关描述 (CG18检测)
- 这不是形式要求——如果你没有交叉验证过数据，你的数据不可信

## 七、上下文与会话管理 — "频繁保存，从不积压"

**R20. 每个Phase完成 = 立即commit**
- `bash scripts/phase_complete.sh {TICKER} {PHASE} {FILE} {MIN_CHARS}`
- Circuit Breaker会阻止有缺陷的commit (exit 4)
- 不要积压超过2个Agent产出不commit

**R21. 并行Agent≥3个时，结果写文件不写inline**
- Agent必须写staging/文件，completion只返回状态+路径
- 防止context溢出 — 这是大报告最常见的失败模式之一

**R22. 用户说"继续"时的恢复协议**
- 读checkpoint.yaml → git log → 立即恢复，不问澄清问题
- 不要重新分析用户意图——checkpoint里有所有信息

## 八、行业特定陷阱

**科技平台 (AAPL/MSFT/GOOGL/META/AMZN)**
- 市值>$2T: 不可能用单一DCF目标价评估。用条件框架: "什么价格水平变便宜"
- AI叙事: 区分"AI收入已实现"和"AI收入是预期"。后者需要更高折扣率
- 监管风险: 不要用概率×影响简单相乘。用条件估值(监管前/后)

**半导体 (NVDA/AMD/TSM/ASML/LRCX/KLAC)**
- 周期性: 用中周期估值(3-5年平均)而非单一年份
- 供应链传导: 上游变化会放大50-100x到下游(AMAT→NVDA传导链)
- 设备vs制造: 设备商用不同于芯片制造商的估值框架

**消费品 (KO/PG/COST/WMT)**
- 数据密度天然低: 用单位经济学/坪效/SKU周转补充硬数据
- 品牌价值: 隐性资产需要独立估值(Kirkland品牌 = COST教训)
- 会员/续费率: 每0.1%变化 = 显著FCF影响

**金融 (JPM/GS/V/MA)**
- 利率敏感性: NII对利率曲线的非线性响应
- 监管资本: Basel要求变化 = 直接影响ROE
- 系数×1.2: 金融报告天然更复杂

## 十、开始前的3个自检问题

1. **我运行了tier3_launch.sh和preflight_gate吗?** 如果没有 → 停下来运行
2. **我的launch_brief目标字符是多少? 我心里有一个杀手级洞见假设吗?** 如果没有 → 在Phase 0时形成
3. **这家公司的可能性宽度是多少? 我应该用传统框架(≤3)还是发现系统(≥7)?** 选错框架 = 浪费大量时间
