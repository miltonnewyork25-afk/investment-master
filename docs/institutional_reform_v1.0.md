# 制度性改革 v1.0 — 从根源上防止"因变量→自变量"类错误

> **日期**: 2026-03-30
> **问题本质**: 不是SBC的问题, 是框架进化系统缺乏自我纠偏能力
> **证据**: v15(KLAC 4.5分, 120行CLAUDE.md) → v19.9(NET 3.8分, 229行+443行铁律+24个skill)
> **结论**: 框架膨胀91%, 质量下降15%。规则不是越多越好。

---

## 一、问题的制度性根源

SBC锚定不是一个孤立事件。它是**三个制度缺陷**的必然产物:

| 缺陷 | 描述 | 后果 |
|------|------|------|
| **只有油门没有刹车** | EVO系统只能增加规则, 没有机制删除/合并规则 | 规则单调递增→框架膨胀→注意力碎片化 |
| **没有"重要性"层级** | 所有规则平级(铁律A和铁律N权重相同) | AI无法区分"核心原则"和"技术细节" |
| **分析工具和投资判断混为一体** | Owner FCF(分析工具)和"增速是否可持续"(投资判断)在框架中地位相同 | AI把计算结果当投资结论 |

---

## 二、制度改革: 三项结构性变化

### 改革1: 框架分层 — 区分"原则"、"工具"、"检查"

**当前问题**: CLAUDE.md + 11条铁律 + 24个skill全部平级。AI读到"核心原则: 分析密度>报告长度"和"铁律N: 三PE并列"时, 认为两者同等重要——但前者是指导思想, 后者是技术操作。

**改革**: 将所有框架内容分为三层, 每层有明确的优先级:

```
Layer 1: 投资原则 (3-5条, 不可违反, 指导方向)
  ——————————————————————————————————————
  这些是"为什么分析"的答案

Layer 2: 分析工具 (模块化, 按需调用, 不指导结论)
  ——————————————————————————————————————
  这些是"怎么分析"的方法

Layer 3: 质量检查 (门控, 完成后验证, 不影响分析方向)
  ——————————————————————————————————————
  这些是"做完了检查一下"的清单
```

**具体分类**:

| Layer | 内容 | 优先级 | 冲突规则 |
|-------|------|:------:|---------|
| **L1原则** | ①业务判断优先于财务发现 ②核心变量必须是业务变量 ③分析密度>报告长度 ④真实数据>编造数字 ⑤可执行建议>宏大叙事 | **最高** | L1 > L2 > L3 |
| **L2工具** | CPA×ISDD/护城河评估/红队套件/估值建模/竞争对标/AI冲击分析 | 中 | 服务于L1, 不能压倒L1 |
| **L3检查** | DM密度/Mermaid数量/因果密度/三PE并列/字符门控/估值离散度 | **最低** | 不影响分析方向, 仅验证质量 |

**关键变化**: 三PE并列/Owner FCF/SBC覆盖率从当前的"铁律级"(L1-L2混合)明确降为**L3检查**(做完分析后检查一下, 不指导分析方向)。

**冲突解决规则**: 当L2工具的发现(如Owner FCF为负)与L1原则(业务判断优先)冲突时, **L1永远胜出**。AI不能因为一个L2工具的计算结果就把它升级为报告的核心结论。

### 改革2: EVO刹车机制 — "话题浓度上限"

**当前问题**: EVO只能增加规则, 没有删除/合并机制。SBC通过5次独立EVO获得了不成比例的框架权重。

**改革**: 引入"话题浓度上限"和"进化衰减":

```
规则1: 话题浓度上限
  框架中任何单一话题(SBC/估值/护城河/增速/...)的提及次数
  不得超过所有话题平均值的2倍。

  检测: 每次新增EVO前自动计算
  违反时: 新EVO必须替代(非叠加)现有规则, 或合并为一条

规则2: 进化衰减
  每条规则有"引入日期"
  引入>6个月且在最近3份报告中未被引用为关键发现 → 自动标记"候选删除"
  引入>12个月且未被引用 → 自动降级为L3

  目的: 让过时的规则自然消亡, 而不是永远积累

规则3: 正面EVO强制
  每增加1条"避免X错误"的负面EVO,
  必须同时增加1条"强化Y成功模式"的正面EVO。

  例: "避免SBC成为核心变量"(负面) + "KLAC成功模式: 围绕不可替代性组织报告"(正面)

  目的: 防止框架变成一个"不要做什么"的清单, 同时保留"应该做什么"的指导
```

### 改革3: "一个问题"测试 — Phase 0.75强制

**当前问题**: 整个分析流程没有一个步骤要求AI回答"这家公司最重要的一个问题是什么"。CQ1-8是并列的, 没有强制排序。

**改革**: Phase 0.75(核心矛盾结晶)后新增"一个问题"测试:

```
Phase 0.75完成后, 必须回答:

  "如果你只能问这家公司一个问题, 你问什么?"

要求:
  1. 必须是业务问题(不可以是会计/成本结构问题)
  2. 这个问题的答案必须能改变你的投资判断的方向(不仅仅是幅度)
  3. 整份报告必须围绕这个问题组织

示例:
  NET: "边缘云平台转型能否成功?" ✅
  NET: "SBC能否收敛?" ❌ (会计问题, 且答案不改变方向——只影响幅度)

  TSLA: "自动驾驶能否实现L4?" ✅
  TSLA: "汽车毛利率能否回升?" ❌ (结果, 非原因)

这个问题在Phase 5执行摘要的第一句话中必须出现。
```

**为什么这能防止SBC类错误**: 如果Phase 0.75就锁定了"一个问题=平台转型", 那后续所有Phase的分析都是为这个问题服务的。即使P2发现了SBC=21%, AI也会在"一个问题"的锚定下将SBC定位为"附属发现"而非"核心结论"。

## 三、实施: 对CLAUDE.md的结构性重组

当前CLAUDE.md 229行, 将重组为分层结构:

```markdown
## 投资原则 (L1, 不可违反)

1. 业务判断优先于财务发现
2. 核心变量必须是业务变量
3. 分析密度 > 报告长度
4. 真实数据 > 编造数字
5. 可执行建议 > 宏大叙事

## "一个问题"测试 (Phase 0.75后强制)

## 分析工具 (L2, 按需调用)
→ 指向各skill和模块文件

## 质量检查 (L3, 完成后验证)
→ 门控/DM/Mermaid/因果密度等

## 铁律 (按L1/L2/L3分类)
```
