# Prompt工程原则 v22.1 — Claude Code四章精华整合

> **来源**: Ch5系统提示词架构 + Ch6行为引导模式 + Ch7模型调优 + Ch8工具提示词设计
> **目的**: 将Claude Code的工业级prompt工程应用于投资调研Agent

---

## 总纲：三层驾驭体系

```
系统提示词(CLAUDE.md) → 设定研究人格和投资哲学
     ↓
铁律/Skill描述(.claude/rules/ + skills/) → 塑造分析动作
     ↓
工具提示词(MCP/Agent/Script) → 约束执行行为
```

**核心洞察**: 优秀的提示词不是功能文档，而是**行为契约**。

## 一、分段记忆化与缓存架构 (Ch5)

### 1.1 段落分类
| 类型 | 变化频率 | 缓存策略 | 投研对应物 |
|------|---------|---------|-----------|
| 稳定段落 | 月级 | 全局缓存 | CLAUDE.md(身份/L0/L1/评级) |
| 低频段落 | 周级 | 行业缓存 | worktree CLAUDE.md(行业定价公式) |
| 易变段落(DANGEROUS) | 每session | 不缓存 | ticker/phase/handoff note |
| 按需加载 | 触发时 | 临时加载用完释放 | .claude/rules/铁律详情 |

### 1.2 静态/动态边界
- **静态区**: CLAUDE.md全部内容 — **NEVER**含session变量(ticker/phase/环境)
- **动态区**: session_context — 每次重新生成
- **边界标记**: 不可移动，静态区不含条件分支
- **因果**: 条件分支侵入静态区 → 缓存命中率从95%暴跌至10%

### 1.3 优先级链
```
L0研究哲学 > L1投资原则 > L2分析工具 > L3质量检查
+ 研究纪律(11条) 始终追加
+ 行业特化 始终追加
```

## 二、6种行为引导模式 (Ch6)

### 2.1 极简主义指令
**在投研中的应用**:
- "NEVER在任务范围外添加分析维度" → 防止"为了全面而全面"
- "低解释力维度≤500字" → 具体数量门槛打破"写满模板"的默认倾向
- "3个承重墙问题/1个Kill Switch/5个跟踪指标" → 数值锚定

### 2.2 渐进式升级
**在投研中的应用**: 分析失败三阶段协议
- 阶段1(诊断): 读错误信息 / 查假设是否仍成立 / 检查数据口径
- 阶段2(调整): 基于诊断做聚焦修复，不推翻整个分析
- 阶段3(求助): 真正的死胡同才标注"需要用户输入"
- **NEVER**盲目重复相同分析方法，也**NEVER**一次数据矛盾就放弃整条thesis

### 2.3 可逆性意识
**在投研中的应用**: 按影响范围分级
| 操作 | 可逆性 | 影响范围 | 规则 |
|------|--------|---------|------|
| 修改staging文件 | 可逆 | 本地 | 自由执行 |
| 更新checkpoint | 可逆 | 本地 | 自由执行 |
| 修改主线thesis | 部分可逆 | 全报告 | 需记录变更理由 |
| 改变评级结论 | 不可逆(已发布) | 读者决策 | 强制反自欺检查 |
| git commit到main | 不可逆 | 永久记录 | 确认分支+质量门控 |

### 2.4 工具偏好引导
**在投研中的应用**: Skill优先级双向闭环
- CLAUDE.md说: "护城河分析用/moat-evaluator，不要手动评估"
- /moat-evaluator说: "护城河评估必须通过本skill执行"
- **双向闭环**比单向约束更有效

### 2.5 Agent委托指引
**在投研中的应用**: 多Agent研究协作
- **Don't peek**: 并行Agent的staging文件不要中途读取 — 等完成通知
- **Don't race**: Agent返回前不要预测其结论 — "fork还在运行"而非猜测
- **Never delegate understanding**: 不要把需要综合判断的thesis形成甩给子Agent
  - ✅ 委托: "查找ASML FY24的EUV出货量和中国收入占比"
  - ❌ 委托: "基于你的发现判断ASML是否被低估"

### 2.6 数值锚定
**在投研中的应用**:
| 输出类型 | 数值锚定 | 替代的模糊描述 |
|---------|---------|-------------|
| 执行摘要 | ≤800字 | "简洁" |
| 低解释力维度 | ≤500字 | "适度" |
| 背景/历史/履历 | 各≤200字 | "精简" |
| Kill Switch | ≥3个信号+阈值 | "几个" |
| 跟踪指标 | 5-8个 | "关键几个" |
| 承重墙问题 | 保留3个 | "核心" |
| 反自欺检查 | ≤60秒/6项 | "快速检查" |

## 三、行为缓解生命周期 (Ch7)

### 3.1 EVO五阶段管道
```
发现(报告验尸) → 引入(evolution_log) → 灰度(1-2份报告验证) →
推广(写入铁律) / 移除(无效/过期) → 季度审计(话题浓度/衰减检查)
```

### 3.2 安全默认值哲学
- **诚实不完整** > 虚假完整（安全默认值）
- **多一条EVO** > 漏掉教训（宁多勿漏）
- **NEVER让EVO密度**导致注意力稀释（SBC锚定Bug = 安全过度的反例）
- **因果解释**让规则在新场景中可泛化（纯命令只在训练分布内生效）

### 3.3 灰度验证实践
- 新EVO先标注"灰度中"，在下1-2份报告中验证
- 对比有/无EVO的报告质量差异（类似A/B测试）
- 6个月未被引用 → 候选删除
- 12个月未被引用 → 自动降为L3

## 四、工具提示词七原则 (Ch8)

### 原则1: 双向闭环
当skill A不应处理某任务 → A说"用B"，B说"必须用我"。
- **投研应用**: 估值分析 → `/valuation-builder` 和 `/valuation-quality-gate` 互相引用

### 原则2: 理由先于禁令
每条NEVER后跟because。模型理解原因后更不易违反。
- **投研应用**: "NEVER硬写，因为虚假确定性导致亏损远大于诚实不确定性"

### 原则3: 能力与运行时对齐
提示词声明的能力必须由运行时保证。
- **投研应用**: 如果MCP工具不可用，不要在报告中声称"已通过FMP验证"

### 原则4: 安全默认值+逃生舱口
保守默认+显式解除方式。
- **投研应用**: DM密度≥1.5/千字(默认) | 用户确认可豁免(逃生舱口)

### 原则5: 预算意识
工具/skill提示词本身消耗token，需要预算控制。
- **投研应用**: 23+个skill的描述需要预算限制，仅激活当前Phase需要的3-5个

### 原则6: 前置条件声明
工具B依赖工具A → 在B中声明，在运行时强制。
- **投研应用**: Phase 1依赖Phase 0.75 → sentinel自动检查(双层防御)

### 原则7: 委派质量标准
约束任务描述的完整性和具体性。Never delegate understanding。
- **投研应用**: 并行Agent的任务描述必须自包含，不能是"基于你的发现做判断"

## 五、跨章节的5个元原则

1. **反面定义 > 正面描述** — "NEVER做X"的边界比"做Y"清晰
2. **具体数字 > 模糊形容词** — "≤800字"没有歧义，"简洁"有
3. **因果解释促泛化** — 解释"为什么"让规则在新场景中可推导
4. **冗余对抗注意力衰减** — 关键规则在CLAUDE.md和discipline.md双位置放置
5. **灰度验证是提示词工程的一部分** — 新规则先验证再推广，像代码变更一样
