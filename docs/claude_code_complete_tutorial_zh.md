## 1. 先思考，再动手

大多数人以为用Claude Code的第一步是开始打字（或说话）。但这恰恰是你能犯的最大错误之一。**你真正需要做的第一件事是思考。**

10次中有10次，我用Plan模式得到的输出都**显著优于**直接开口说话的结果。差距不是一点半点。

如果你缺乏软件工程经验来独立思考架构问题，有两个建议:

1. **开始学习。** 如果你从不培养这个能力，你就是在给自己设障碍。哪怕每次只学一点点也好。
2. **和ChatGPT/Gemini/Claude进行深度对话。** 描述你想构建什么，让LLM列出系统设计的各种选项，然后双方共同敲定方案。你和LLM应该**互相提问**，而不是单向输出。

这适用于所有场景，包括像"总结邮件"这样的小任务:
- 让Claude构建功能之前 → 先想清楚架构
- 让Claude重构代码之前 → 先想清楚目标状态
- 让Claude调试之前 → 先想清楚你对问题已知的信息

**你在Plan模式中提供的信息越多，输出就越好，因为输入更好了。**

规律始终如一: **先思考再打字**的效果远胜于**先打字再期望Claude能搞定**。

### 架构的重要性

架构设计，尤其在软件工程中，就像只告诉一个人"最终产出"但不给任何其他信息。这留下了**巨大的自由发挥空间**——而这恰恰是AI生成代码的核心问题。

对比:
- **模糊**: "帮我建一个认证系统"
- **精确**: "用现有的User模型构建邮箱/密码认证，将session存储在Redis中并设置24小时过期，添加中间件保护/api/protected下的所有路由"

你按两次 `Shift+Tab` 就能进入Plan模式。相信我，这只花你5分钟，但能在后续调试中帮你省下几个小时。

## 2. CLAUDE.md 文件

CLAUDE.md是一个Markdown格式文件。Markdown是AI模型处理得非常好的文本格式，而Claude在处理Markdown方面比我测试过的大多数其他模型都要出色。

**当你启动Claude Code会话时，Claude做的第一件事就是读取你的CLAUDE.md文件。** 文件中的每条指令都会影响Claude处理你项目的方式。它本质上是Claude在每次对话前都会阅读的"入职培训材料"。

大多数人要么完全忽略它，要么往里面塞一堆垃圾信息，反而让Claude变得更差。**信息太多或太少都会导致模型输出变差，存在一个最佳阈值。**

### 真正重要的原则

**保持简短。** Claude一次能可靠遵循大约**150到200条指令**，而Claude Code的系统提示词已经占用了大约50条。你添加的每条指令都在争夺注意力。如果你的CLAUDE.md写成了一本小说，Claude会开始**随机忽略**其中一些内容，而你根本不知道忽略了哪些。

**针对你的项目定制。** 不要解释"components文件夹是什么"——Claude知道什么是components。告诉它那些**怪异的、特殊的东西**，比如真正重要的bash命令。所有属于你工作流程的内容都应该写进去。

**告诉它"为什么"，不仅仅是"做什么"。** Claude在这方面有点像人类。当你给出指令背后的原因时，Claude的执行效果比只告诉它做什么要好。
- 一般: "使用TypeScript严格模式"
- 更好: "使用TypeScript严格模式，因为我们曾因隐式any类型在生产环境中出过bug"

**"为什么"给了Claude上下文来做出你没有预料到的判断。** 这个效果好到你会感到惊讶。

**持续更新。** 在工作时按 `#` 键，Claude会自动向你的CLAUDE.md添加指令。每当你发现自己在同一件事上纠正Claude两次，那就是一个信号——这条内容应该写进CLAUDE.md。随着时间推移，你的CLAUDE.md会变成一份活文档，记录着你的代码库真正是如何运作的。

### 好坏对比

- **差的CLAUDE.md**: 像写给新员工的入职文档
- **好的CLAUDE.md**: 像你知道明天会失忆时给自己留的笔记

## 3. Context窗口的局限性

以Opus 4.5为例，它有200,000 token的上下文窗口。但大多数人没有意识到: **模型在远未达到100%之前就开始退化了。**（具体退化程度取决于你是通过API还是桌面应用使用）

**大约在20-40%的上下文使用率时，输出质量就开始下滑**，即使下滑幅度还不太明显。如果你经历过Claude Code进行compaction之后输出仍然很差的情况，原因就在这里——**模型在compaction发生之前就已经退化了**，而compaction并不能神奇地恢复质量。（输入 `/compact` 进行压缩）

你发送的每条消息、Claude读取的每个文件、它生成的每段代码、每个工具返回结果——**全部在累积**。一旦质量开始下降，更多的上下文只会让情况更糟，而不是更好。

### 有效应对策略

**划分对话范围。** 一个对话只做一个功能或一个任务。不要用同一个对话来构建认证系统然后又重构数据库层。不同的上下文会**相互渗透**，Claude会变得混乱。我知道你们中至少有一个人犯过这个错误。

**使用外部记忆。** 如果你在做复杂工作，让Claude把计划和进度写到实际文件中（我用`SCRATCHPAD.md`或`plan.md`）。这些文件能**跨会话保留**。当你第二天回来时，Claude可以读取文件从上次停下的地方继续，而不是从零开始。附注: 如果你有一个文件层级体系，把这些文件放在最顶层可以让它们对你构建的每个任务/功能都起效。

**复制-粘贴重置法。** 这是我经常用的技巧: 当上下文膨胀时，我把终端中所有重要内容复制出来，运行 `/compact` 获取摘要，然后 `/clear` 彻底清空上下文，最后只粘贴回真正重要的内容。**干净的上下文配上关键信息**，比让Claude在退化的上下文中挣扎好太多了。

**知道何时清空。** 如果对话已经跑偏或积累了大量无关上下文，直接 `/clear` 重新开始。这比试图在混乱中继续工作要好。Claude仍然会读取你的CLAUDE.md，所以你不会丢失项目上下文。**10次中有9次，使用clear实际上比不使用更好**，尽管这听起来违反直觉。

### 核心心智模型

**Claude是无状态的。** 每次对话都从零开始，除了你显式提供的信息之外。据此来规划你的工作。

## 4. 提示词就是一切

人们花几周时间学习框架和工具，却花**零时间**学习如何与真正生成代码的东西沟通。

提示不是什么神秘艺术。它可能是**最基本的沟通形式**。就像任何沟通一样，清晰总是比模糊得到更好的结果。每一次。

### 有效做法

**明确说明你想要什么。** "建一个认证系统"给了Claude它会滥用的创意自由。"用现有的User模型构建邮箱/密码认证，将session存储在Redis中，添加中间件保护/api/protected下的路由"给了Claude一个清晰的目标。即便如此这还不够完美。

**告诉它不要做什么。** Claude有自己的倾向。**Claude 4.5尤其喜欢过度工程化**——多余的文件、不必要的抽象、你没要求的灵活性。如果你想要简单的东西，就说"保持简单。不要添加我没要求的抽象。如果可能的话只用一个文件。"另外，永远要交叉检查Claude的产出，因为你不想积累技术债务——尤其是当你构建一个非常简单的东西，结果它给你建了12个文件来完成一个实际上几行代码就能解决的任务。

**必须记住: AI的设计目的是加速我们，而不是完全替代我们**，尤其是在专业软件工程领域。Claude仍然会犯错。我相信它会继续犯错，即使会随时间变得更好。所以**能够识别这些错误**实际上能解决你很多问题。

**提供"为什么"的上下文。** "我们需要这个速度快，因为它在每个请求上都会运行"会改变Claude处理问题的方式。"这是一个我们会扔掉的原型"会改变哪些权衡是合理的。Claude无法读取你脑中那些你没有提到的约束条件。

**记住: 输出就是一切，但它只来自输入。如果你的输出很烂，那是因为你的输入很烂。这一点无法绕过。**

## 5. 差输入 = 差输出

当人们得到糟糕的结果时，他们会怪模型。"Claude不够聪明"或"我需要更好的模型。"

**现实检查: 问题在你。** 如果你用像Opus 4.5这样的好模型却得到差输出，说明你的输入和提示词能力不行。就这么简单。

模型确实很重要，非常重要。但在当前阶段，模型质量已经是基本门槛。**瓶颈几乎总是在人的一侧**: 你如何构建提示词、如何提供上下文、你多清楚地传达你真正想要什么。

如果你持续得到差结果，解决方案不是换模型。解决方案是提升:

- **如何写提示词**: 具体 > 模糊。约束 > 开放式。示例 > 描述。
- **如何组织请求**: 把复杂任务拆分成步骤。在实现之前先就架构达成一致。审查输出并迭代。
- **如何提供上下文**: Claude需要知道什么才能做好这件事？你做了哪些Claude看不到的假设？

### 模型差异

- **Sonnet**: 更快、更便宜。擅长**路径清晰的执行任务**——写样板代码、按照明确计划重构、实现你已经做好架构决策的功能。
- **Opus**: 更慢、更贵。擅长**复杂推理、规划，以及需要Claude深入思考权衡**的任务。

**有效的工作流**: 用**Opus做规划和架构决策**，然后切换到**Sonnet**（Claude Code中按`Shift+Tab`）做实现。这取决于你的任务，有时候实现阶段也可以用Opus。不过如果你通过API来做这个，你可能要考虑卖肾了。你的CLAUDE.md确保两个模型在相同约束下运行，所以交接是干净的。

## 6. MCP、工具和配置

Claude有大量功能: MCP服务器、Hooks、自定义斜杠命令、settings.json配置、Skills、插件。

**你不需要全部用到。但你应该真正去尝试和实验。** 因为如果你不实验，你可能在浪费时间或金钱。我保证Claude至少有一个你不知道的新功能正在推出。

### MCP (Model Context Protocol)

让Claude连接到外部服务: Slack、GitHub、数据库、API。如果你发现自己不断从某个地方复制信息粘贴到Claude，那可能有一个MCP服务器可以自动完成。有大量MCP市场，如果没有现成的MCP，它本质上就是一种获取结构化数据的方式，所以你可以为任何你需要的工具创建自己的MCP服务器。我会非常惊讶如果你找到一个不存在的。

### Hooks

让你在Claude做出更改**之前或之后**自动运行代码。
- 想让Prettier在Claude修改的每个文件上运行？→ Hook
- 想在每次编辑后做类型检查？→ Hook

这能**立即**捕获问题，而不是让它们堆积。这也是消除技术债务的好方法。如果你在每千行代码后设置一个特定的Hook，你就有了一个安全功能来潜在地清理你的代码。当Claude审查你的PR时也应该很有帮助。

### 自定义斜杠命令

就是你反复使用的提示词，打包成命令。创建一个`.claude/commands`文件夹，添加包含你提示词的markdown文件，然后你就可以用`/commandname`来运行。如果你经常运行同一类任务——调试、审查、部署——把它做成命令。

### 保持好奇心

如果你有Pro Max计划（我每月付$200），为什么不试试Claude提供的所有功能？看看什么有效什么无效。反正你已经付了钱。

**不要因为第一次尝试失败就放弃。** 这些模型基本上每周都在改进。一个月前不好用的东西现在可能好用了。做一个早期采用者意味着保持好奇心和不断重新测试。

## 7. 当Claude卡住时

有时候Claude就是会循环: 它尝试同一件事，失败，再尝试，再失败，如此反复。或者它自信满满地实现了一个完全错误的东西，你花二十分钟试图解释为什么它是错的。

当这种情况发生时，你的本能是继续推。更多指令、更多纠正、更多上下文。但现实是，**更好的做法是完全改变方法。**

**从简单做起——清空对话。** 累积的上下文可能在让它困惑。`/clear` 给你一个全新的开始。

**简化任务。** 如果Claude在一个复杂任务上挣扎，把它拆成更小的部分。先让每个部分单独工作，再组合。但实际上，如果Claude在一个复杂任务上挣扎，那意味着**你的Plan模式做得不够充分**。

**展示而非讲述。** 如果Claude一直误解你想要什么，自己写一个最小的示例。"这是输出应该是什么样子的。现在把这个模式应用到其余部分。" Claude**非常擅长**理解成功标准是什么样的，然后按照好的示例执行。

**发挥创意。** 尝试一个不同的角度。有时候你表述问题的方式不太匹配Claude的思维方式。重新表述——"把这个实现为状态机" vs "处理这些转换"——可能就能突破僵局。

### 元技能

这里的元技能是**尽早识别你是否陷入了循环**。如果你已经解释同一件事三次而Claude还是没明白，更多的解释不会有帮助。**改变策略。**

## 8. 构建系统，而非一次性使用

从Claude获得最大价值的人不是用它做一次性任务。他们在**构建系统**，而Claude是其中的一个组件。

Claude Code有一个 **`-p` 标志**用于无头模式(headless mode)。它运行你的提示词并输出结果，无需进入交互界面。这意味着:
- 你可以**脚本化**它
- 将输出**传递给其他工具**
- 用bash命令**链式调用**
- 集成到**自动化工作流**中

企业正在用这个做: 自动PR审查、自动客服工单响应、自动日志和文档更新。全部可记录、可审计，并且随时间基于什么有效什么无效来持续改进。

### 飞轮效应

Claude犯了一个错误 → 你审查日志 → 你改进CLAUDE.md或工具 → **Claude下次做得更好**。这会复利增长。

> 我目前正在实现让Claude自己改进自己的CLAUDE.md文件的能力。经过几个月的迭代，用这种方式构建的系统比刚上线时明显更好——**同样的模型，只是配置更好了**。

如果你只在交互模式下使用Claude，你在浪费价值。想一想在你的工作流中**哪里Claude可以在无人监督的情况下运行**。

## TLDR 核心要点

1. **先思考再打字。** 规划产出的效果远胜于直接开口说话。
2. **CLAUDE.md是你的杠杆点。** 保持简短、针对性强、告诉它为什么、持续更新。这个文件影响每一次交互。
3. **上下文在30%就开始退化，不是100%。** 使用外部记忆、限制对话范围，不要怕用"复制-粘贴重置法"来清空和重新开始。
4. **架构比什么都重要。** 你不能跳过规划。如果你不先想清楚结构，输出就会很差。
5. **输出来自输入。** 如果你用好模型却得到差结果，你的提示词能力需要提升。学会更好地沟通。
6. **实验工具和配置。** MCP、Hooks、斜杠命令。如果你在付Pro Max的费用，就把所有东西都试一遍。保持好奇心，即使第一次失败。
7. **卡住时改变方法。** 不要循环。清空、简化、展示、重新表述。
8. **构建系统，而非一次性使用。** 无头模式、自动化、记录改进过程。

---

> 如果你在用Claude构建——无论是个人项目还是生产系统——这些原则决定了你是在**和工具对抗**还是在**与工具协同**。
