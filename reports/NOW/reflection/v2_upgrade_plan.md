## Phase 1: 3个EVO落地 (框架资产, 惠及全部未来报告)

### EVO-NOW-01: SBC $9B临界点模型泛化

**问题**: NOW的SBC从19.2%→14.7%(-4.5pp/4年)在收入达到$9B后启动收敛。这是NOW独有现象还是SaaS通用规律?

**提议**: 创建 `knowledge/analysis_modules/sbc_tipping_point_model.md`
- 用6家SaaS公司(NOW/CRM/ADBE/WDAY/DDOG/SNOW)的SBC/Rev vs Revenue数据, 验证是否存在通用"临界收入规模"
- 如果验证→每份SaaS报告Phase 1 SBC分析时自动引用
- 如果否定→标注"NOW的收敛是个案"

**内容**:
1. 6家SaaS的SBC/Rev × Revenue散点图→是否存在"拐点"?
2. 拐点触发机制假说(规模效应/股东压力/招聘效率)
3. 预测模型: 给定Revenue规模→预期SBC/Rev范围
4. Kill Switch: 实际SBC/Rev偏离预测>3pp→收敛假说失败

**适用**: 所有SBC/Rev>15%的SaaS公司
**工作量**: 2小时(数据收集+分析+写入)

### EVO-NOW-02: CQ方向一致性自动检测

**问题**: NOW的7个CQ从P0到P3全线上调(7/7), 概率仅2.8%→高度暗示确认偏差。P4偏差审计才发现, 但如果Phase 3就能自动检测→节省1个Phase的偏差传播。

**提议**: 在 `scripts/phase_sentinel.sh` Layer 3中增加CQ方向检测:
```bash
# CQ方向一致性检测 (Phase 3后自动执行)
# 如果N/N个CQ同方向移动(全上调或全下调)→WARNING
# 阈值: 如果≥5个CQ同方向→概率<10%→触发WARNING
# 如果≥7个CQ同方向→概率<3%→触发BLOCK(强制Phase 4红队优先)
```

同时在 `cq-lifecycle-tracker` skill中增加:
- "方向一致性得分": 如果P0→PN所有CQ同方向→得分=N/Total→>0.7=WARNING
- 自动生成"最可能的反方向CQ"建议→红队优先攻击

**适用**: 所有Tier 3报告
**工作量**: 1小时(脚本+skill更新)

### EVO-NOW-03: DM密度/因果密度权衡框架

**问题**: NOW因果密度13.9/万字(全报告最高)但DM密度0.95/千字(全报告最低)。当前质量标准将两者独立门控(DM≥1.5, 因果≥5.0)→NOW被D1(6.5)严重拖累, 但分析深度实际最高。

**提议**: 在 `docs/quality_standard_4.4.md` 中增加"质量互补规则":
```
DM密度 × 因果密度 = "分析诚信度"
  如果DM≥1.5且因果≥5.0 → 标准通过
  如果DM<1.5但因果≥10.0 → "分析深度补偿" → D1最低6.5(非0)
  如果DM≥2.0但因果<5.0 → "数据堆砌"(大量引用但无推理) → D3 cap at 6.0

核心理念: DM是"引用纪律"(可以通过backfill提升), 因果是"思维深度"(不可事后补)
→ 因果密度>>DM密度时, 优先补DM而非惩罚分析深度
```

**适用**: 所有报告的D1/D3评分
**工作量**: 30分钟(规则文档更新)
