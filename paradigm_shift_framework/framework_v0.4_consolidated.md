**Status**: production Layer 0, executable

**Position**: upstream diagnostic layer before `framework_v1.1.md`
**Core scope**: production-grade framework for turning state-change control analysis into repeatable investment research.
- **M14 平台层 (Platform Layer)** — 评估 API / MCP / Marketplace 是否形成平台期权或后端化风险

## One-Line Thesis (v0.4 主钉子句)

> **AI 功能强, 不等于 AI 第二曲线强。只有当状态变化能被验证、归因、写回、回滚、收费, AI 才从"聪明功能"变成投资意义上的第二曲线。**

Compressed:

> Whoever can prove it can change high-value states cheaply, auditably, attributably, and responsibly can control the new AI-era profit pool.

## 4 Prompt Constraints (v0.4 强化)

每次分析前强制 enforce:

1. 如果公司不能用 `object: old state -> new state` 表达, 停。
2. **如果公司在不同业务线有 ≥3 个发散的 M11/M12/M13, 强制 SOTP, 不允许整体打分**
3. 不要把内容生成等同于业务状态改写。
4. 不要把数据等同于状态变量或控制变量。
5. 不要在没有付费证据或预算迁移证据的情况下声称 TAM 重写。

## 13 Hard Questions + Q14 (v0.4 新增)

1. 公司控制什么状态变化?
2. 这个状态变化是否高频、高价值、高摩擦、责任可转移、可标准化?
3. 数据是否升级为状态变量或控制变量?
4. 状态变量是否有真实验证源?
5. 公司是否定义行业 object / state machine / permission / interface / audit / rollback 规则?
6. 能不能从 read-only insight 升级到 state rewriting?
7. 写到哪里: UI / 工作流 / SoR / 外部系统 / 监管 / 交易 / 生产系统?
8. 是不是闭环 (sense / decide / execute / feedback / correct / rollback)?
9. AI 等级和责任 + 写入深度是否匹配?
10. 责任能不能转移, 收费能不能从 seat 迁到 usage / task / outcome / risk-sharing?
11. 结果改善能不能在因果上归因到公司, 并被客户接受为付费基础?
12. 是不是从软件预算迁移到人工/外包/服务/风险/结果预算?
13. 复杂度是复利资产还是交付负担, 谁最终捕获利润池?
14. **(NEW v0.4)** 如果公司有平台层 (API/MCP/Marketplace), 第三方 agent 能否通过它调用; 这是保护还是被抽象成后端?

# M2. State-Change Quality and Clock Speed (v0.4 — 加入行业基准)

**Question**: 状态变化值不值得控制, 反馈速度能不能复利?

Score each 0-3:

| Dimension | 0 | 3 |
|---|---|---|
| Frequency | Annual / one-off | Daily / hourly |
| Value | Low consequence | High revenue / cost / risk impact |
| Friction | One person, one system | Multi-person, multi-system, multi-step |
| Responsibility transferability | Hard to audit / contract | Auditable, contractible, insurable, layered |
| Standardization | Fully bespoke | Repeatable object + workflow |

### v0.4 新增 — 行业时钟速度参考线

时钟速度不是公司变量, 是行业天花板:

| 行业 / 业务类型 | 反馈周期 | 时钟分类 | 例子 |
|---|---|---|---|
| 报税 / 支付 / 代码部署 / Ad ROAS | 秒-小时 | **Fast (compounder)** | INTU TurboTax / Stripe / GitHub Actions / Google Ads |
| SMB 月结 / Payroll / 邮件 CTR | 日-周 | **Fast (compounder)** | INTU QBO / Mailchimp |
| 工业 PLM ECN / Field Service / Codebeamer test | 周-月 | **Mid compounder** | PTC Windchill / Codebeamer / ServiceMax |
| 制造 BOM 变更影响 | 月-季 | **Mid compounder** | PTC / Siemens Teamcenter |
| AEC 设计协调 → 施工反馈 | 6-18 月 | **Slow compounder (R-CLOCK 触发)** | ADSK Revit / BIM360 |
| 大基建 / 航空 / 国防工程 | 1-5 年 | **Very slow (R-CLOCK 强触发)** | Bentley / Dassault 国防 |
| 创意效果 / 品牌建设 | 周-季 (但归因弱) | **Fast frequency, 弱归因** | ADBE Firefly / Canva |

R-CLOCK: 如果 state change 反馈 ≥1 季度, 复利天花板压在 mixed (而非 compound)。

R-CLOCK-STRONG (v0.4 新): 如果 state change 反馈 ≥1 年, AI 第二曲线评分上限 = 3.0/5。

# M3. Data to State Variable

**Question**: 公司持有的是普通数据、状态变量, 还是控制变量?

Four levels:

```text
1. Raw data: 仅信号
2. Structured data: 可查询 schema
3. State variable: 描述当前业务状态
4. Control variable: 触发动作 + 接收结果反馈
```

Score each 0-3:

| Test | Question |
|---|---|
| Frequency | 数据持续刷新? |
| Exclusivity | 专有或难复制? |
| Verifiability | 有 ground truth? |
| Actionability | 能触发动作? |
| Feedback | 动作结果回流? |

R-VERIFY: 没有 ground-truth source → cap data level at state variable, 不到 control variable。

# M4. Semantic Authority

**Question**: 公司是否定义行业操作语言?

Score each 0-4:

| Right | What It Means |
|---|---|
| Object definition | 定义 lead / ticket / claim / invoice / deployment / tax return / ECN / BOM / requirement 等 |
| State-machine definition | 定义 object 如何在状态间迁移 |
| Permission definition | 定义谁能 read / write / approve / reject |
| Interface definition | 定义 API 和集成默认 |
| Audit / rollback definition | 定义什么算 record / evidence / correction |

Classification:

```text
0-4: 用别人语言的参与者
5-9: 产品级语义
10-15: 跨客户语义层
16-20: 行业操作语言候选
```

语义权强于数据量。它定义 AI agent 能在哪里行动。

# M5. Write Rights

**Question**: 公司能否改写业务状态, 写到哪里?

Execution level:

```text
L0 Read-only insight
L1 Suggested action
L2 Human-approved execution
L3 Write-enabled execution
L4 Autonomous operation with exception handling
```

Write-depth ladder:

```text
D1 UI / document layer
D2 Workflow system
D3 System of record
D4 External customer / partner system
D5 Regulated, transaction, payment, or production system
```

Important distinction:

```text
L4 × D1 = autonomous but shallow
L2 × D5 = human-approved but high-value
L3 × D3 = core SaaS AI execution battleground
```

**v0.4 强化**: 没有 D2+ 写入权 → C 类 M5 cap at 4/8 (G3 Hard Gate)。

# M7. AI Second-Curve Reality

**Question**: AI 是增强老产品还是创造第二曲线?

AI level:

```text
L1 AI feature: search, summary, generation
L2 Copilot: improves human productivity
L3 Workflow executor: executes part of a workflow
L4 Closed-loop agent: completes and writes back
L5 Autonomous operator: handles exceptions within boundaries
L6 Industry operating layer: defines objects, interfaces, audit, responsibility
```

Practical 0-5 interpretation:

```text
0: no substantive AI
1: AI feature
2: copilot efficiency
3: workflow executor with limited monetization
4: closed-loop execution with pricing evidence
5: outcome / responsibility-backed operator
```

**v0.4 红线 (R-CLOCK-STRONG)**: 如果 M2 触发 R-CLOCK-STRONG (反馈 ≥1 年), AI 第二曲线分上限 = 3.0/5。

# M10. Competitive Capture

**Question**: 谁控制利润池?

Five gates:

| Gate | Control Question |
|---|---|
| Data gate | 谁拥有专有 / 高频 / 可验证 / 反馈丰富的数据? |
| Semantic gate | 谁定义 object 和 state machine? |
| Permission gate | 谁能 read / write / approve / rollback / audit? |
| Responsibility gate | 谁能接受责任? |
| Distribution gate | 谁已经在默认工作流里? |

Attack matrix:

| Actor | Usually Attacks | Usually Blocked By |
|---|---|---|
| Frontier model company | language, search, generation, light workflow | private state, permissions, audit, liability |
| AI-native startup | cross-silo whitespace, poor UX, high-labor tasks | SoR, compliance, enterprise distribution |
| Customer self-build | internal orchestration, workflow glue | shared semantics, cross-customer learning, liability |
| Services firm with AI | implementation, BPO, consulting workflow | productized IP, repeatable platform economics |
| Incumbent SaaS | SoR, permissions, data, procurement | failure to upgrade into execution |

利润通常归属于控制最多门 + 接受足够责任以超 seat 收费的 actor。

# M11. Responsibility Transferability (v0.4 — Tier 5 显性化)

**Question**: 责任能否以商业形式从客户转移到 vendor?

Responsibility ladder:

```text
Tier 1 Software access: seat / subscription, no result responsibility
Tier 2 AI assist: add-on / usage, weak responsibility
Tier 3 Workflow automation: task pricing, task-level responsibility
Tier 4 Outcome delivery: outcome pricing, result responsibility
Tier 5 Risk sharing: success fee / insurance / balance-sheet risk
```

### v0.4 新增 — Tier 5 最低门槛 (Tier 5 floor)

Tier 4 → Tier 5 的边界必须更精确:

Tier 5 必须同时满足以下 ≥4 项 (硬门槛):

| 条件 | 检验 |
|---|---|
| 1. 资本承担 | Vendor balance sheet 真实承担 (非保险公司分担) |
| 2. 保险池 | 有 \$X+ insurance pool, 行业再保愿意承保 |
| 3. 监管接受 | 监管/法院/审计接受 vendor 责任为最终责任 |
| 4. 历史理赔 | 至少 1 次大规模 (\$10M+) 理赔事件经验 |
| 5. 合同结构 | success fee / risk-sharing / insurance-style 收费占主要业务 ≥30% |
| 6. 客户付费验证 | 客户为"风险承担"而非"软件使用"付溢价 |

例:
- INTU TurboTax \$100K accuracy guarantee = **Tier 4** (有合同 + 有理赔, 但单笔 cap 较小, 资本承担有限)
- 假想 Tier 5 = vendor 完全代替客户面对监管, 像专业保险公司一样运营 (目前四家公司都未达到)

Score each 0-3:

| Condition | What to Check |
|---|---|
| Permission boundary | RBAC, write whitelist, scoped execution |
| Audit chain | evidence logs, SOC2 / SOX / HIPAA / industry audit |
| Human-in-the-loop | default human review for high-risk actions |
| Rollback / remedy | rollback API, compensation, exception handling |
| Contract structure | SLA, outcome guarantee, indemnity |
| Regulatory acceptance | regulator / court / auditor accepts the workflow |
| Transferability | responsibility can be audited, insured, contracted, layered |

高责任 + 低 transferability = 不是好商业模式, 是商业化瓶颈。

# M12. Causal Attribution

**Question**: 结果改善能否在因果上归因到这家公司的系统?

Score each 0-3:

| Test | Question |
|---|---|
| Measurement | 结果在 state-change 层被测量? |
| Counterfactual | 能与 baseline / holdout / prior process 比较? |
| Confound control | 能分离公司影响与客户劳动 / 宏观 / 第三方工具? |
| Auditability | 客户能验证为什么结果改变? |
| Payment acceptance | 客户接受这个归因为付费基础? |

R-CAUSAL:

```text
No causal attribution = no outcome pricing.
Weak attribution = usage / task pricing only.
Strong attribution = outcome pricing can enter the base case.
```

常见陷阱: 公司创造价值, 但客户不同意公司导致价值。

# M13. Value Capture (v0.4 — 4 路泄漏诊断标准化)

**Question**: 谁捕获状态变化创造的经济价值?

Score each 0-3:

| Test | Question |
|---|---|
| Economic surplus | 创造的客户价值多大? |
| Share-of-surplus | 公司能拿走 surplus 中多少? |
| Pricing power | 转换成本 / 标准 / 责任足以维持价格? |
| Competitive leakage | 模型商 / startups / 服务商 / 客户会捕获价值吗? |
| Margin retention | 模型 / 计算 / 服务成本后, 公司保留毛利? |

### v0.4 新增 — 4 路泄漏诊断 (强制输出)

每家公司必须填写 4 路泄漏强度 (低 / 中 / 高):

| 泄漏路径 | 检验 |
|---|---|
| → 模型商泄漏 | OpenAI/Anthropic 抽走 token cost / API margin? |
| → 服务商泄漏 | Accenture/Deloitte 拿走 AI 实施咨询预算? |
| → 客户自建泄漏 | 大客户用 GPT-4 + 内部数据自建, 取消订阅? |
| → 新进入者泄漏 | vertical AI startup / agent platform 抢入口/语义? |

R-CAPTURE:

```text
Value creation without value capture is not an investment moat.
If surplus flows mostly to customers or competitors, do not award AI second-curve premium.
```

R-LEAK4 (v0.4 新): 如果 4 路中 ≥3 路是"高泄漏", **AI 第二曲线评分上限 = 3.0/5**, 即使其他模块得分高。

# M14. Platform Layer (NEW v0.4)

**Question**: 公司有没有 API/MCP/Marketplace 平台层, 第三方 agent 能否通过它调用; 这是保护还是被抽象成后端?

AI 时代需要单独评估公司是否成为 agent 可调用的平台层, 以及这种平台化是保护还是被抽象成后端。

Score each 0-1:

| Dimension | Check |
|---|---|
| API existence | 有公开 API? |
| MCP / agent protocol | 支持 MCP / Function Calling / Agent SDK? |
| Marketplace | 有第三方 agent / app marketplace 商业化? |
| Take-rate / usage revenue | 平台收入有商业化模式 (take-rate, usage)? |
| Certification | 有第三方 agent 认证机制? |

**双刃判断**:
- **保护信号**: 第三方 agent 必须用公司 API, 公司收 take-rate / usage revenue → 平台经济正向
- **风险信号 (R-ABSTRACT)**: 如果第三方 agent 通过 API 完成 80%+ 用户操作, 用户不再进公司 UI → 公司沦为后端 data provider, seat 经济崩塌

期权评分 (0-5 加分):

```text
0:  无平台 (默认)
1-2: API 存在但无商业化
3:  Marketplace 上线 (v2.0+ 测试期)
4:  Marketplace + take-rate 商业化 (P2)
5:  Marketplace 财务化 (P3, 单独披露 revenue)
```

例:
- ADSK APS + MCP + Marketplace = M14 = **3** (Marketplace 上线但未 P3 财务化)
- INTU = M14 = **1** (有 API 但无 marketplace economics)
- ADBE = M14 = **2** (Adobe agentic ecosystem 有 partnerships, 无 marketplace)
- PTC = M14 = **1** (Onshape / Windchill 有 API, 无 marketplace economics)

### 一致性失败权重分级 (v0.4 新)

失败 1 个和失败 5 个不能同等处理, 因此一致性失败按权重分级:

| 失败数 | 影响 |
|---|---|
| 0 | 无影响 (优秀信号) |
| 1 | -2 分 (从 100 分扣) |
| 2 | -5 分 |
| 3 | -10 分 + 评级降一档 |
| 4-5 | -15 分 + 评级降两档 + 强制 SOTP |
| 6+ | 整体打分作废, 必须按业务线拆 |

特殊权重 (核心一致性失败加重):
- C7 (M11+M12) 失败 = -3 分加扣 (outcome pricing 不可成立)
- C10 (M2+M6) 失败 = -2 分加扣 (慢时钟限制复利)
- C12 (M2+M13) 失败 = -3 分加扣 (慢时钟 + 多路泄漏)

## Final Output Requirements (v0.4 强制结构)

每份分析报告必须包含:

### 必须 1: 主矛盾句 (Main Contradiction)
> 一句话讲市场把这家公司当什么 vs 报告认为它真的是什么。差异是什么。

### 必须 2: 业务场景叙事 (Business Scenario)
> 用客户角色 (老板/PM/品牌经理/工程师) 描述他们真正想要什么 — 减抽象词。

### 必须 3: 主图压缩 (One-Line Summary)
```text
{Company} is not just {old product label}; it is trying to control {object: old state -> new state},
with {write depth}, {responsibility tier}, {attribution strength}, and {value-capture quality}.
```

### 必须 4: 14 模块打分 (M1-M14)
每个模块 Yes/Partial/No + Evidence (E 等级) + Counter-evidence + Investment implication + 4-8 quarter monitor。

### 必须 5: 100 分制 6 类记分 + M14 期权加分
每类拆解 + 红线检查 (G1-G7) + 一致性 C1-C12。

### 必须 6: 反方最强论证 (Strongest Bear Case)
一句话 + 5 条逻辑链, 必须能压力测试主结论。

### 必须 7: 估值与预期差 (Valuation Bridge)
4 列: 市场当前 price-in / 报告分歧 / 上修触发 / 下修触发。
估值语言分叉 (PE 倍数 / SOTP / 平台期权打折等)。

### 必须 8: Kill Switch + 4-8 季度监控
每家 ≥3 个 Kill Switch + ≥6 个监控指标 (附 E 等级)。

### 必须 9: Final 10-Item Output
1. 核心状态变化一句话
2. 当前层级 (tool / data / SoR / workflow / copilot / closed-loop / 责任层 / 行业标准 / 利润池控制)
3. AI 第二曲线 0-5 分 (含 M7 + M11 + M12 + M14 证据)
4. 最大客观约束
5. 最大主观管理层选择
6. 最可能攻击的利润池
7. 最可能被谁攻击
8. 复杂度: compound / mixed / burden
9. TAM 重写: LOW / MEDIUM / HIGH / VERIFIED, 含 P0-P4 证据 (要求细分: "整体 P3 / 局部 P4 / AI 单独 P1-P2" 格式)
10. 4-8 季度监控指标 (跨产品 / 商业化 / 成本 / 护城河 4 类)
