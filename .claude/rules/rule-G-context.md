### G1: 压缩触发感知 (200K窗口基准)

> **原理**: Claude Code在上下文达到83.5%时自动触发压缩。理解这个机制才能提前行动。

**关键阈值** (200K窗口):
| 阈值 | Token数 | 占比 | 含义 |
|------|---------|------|------|
| 有效窗口 | 180K | 90% | 原始窗口-20K压缩输出预留 |
| **自动压缩触发** | **167K** | **83.5%** | 有效窗口-13K缓冲 |
| 预警区 | 147K | 73.5% | 触发点-20K，进入危险区 |
| 阻塞硬限制 | 177K | 88.5% | 有效窗口-3K，最后防线 |

**Agent行为规则**:
1. **Phase中期自检**: 每写完一个大章节(≥15K字符)，评估当前context消耗。如果感觉"压力大"(工具返回变慢/摘要变多)→主动保存
2. **Phase完成时**: 必须执行`context_save.sh`，不积压到下一Phase
3. **进入预警区(≈150K tokens)**: 立即完成当前段落→`context_save.sh`→主动`/compact`

### G2: 压缩丢失感知 (什么最容易被压没)

> **Ch9关键发现**: 压缩后最多恢复5个文件/50K tokens/单文件5K。以下信息类型最脆弱:

**高丢失风险** (必须提前持久化):
1. **被否决方案的原因** — 压缩模板侧重"做了什么"，"为什么不做X"容易丢失
2. **早期细微偏好** — 对话开头提过的约束(如"不要用某方法")，多次压缩后消失
3. **精确代码diff** — 超长diff会被截断，只保留摘要
4. **跨Phase推理链** — Phase 1的洞察到Phase 3时可能已被压缩成一句话

**应对**: 关键约束写入CLAUDE.md(免疫压缩) | 每Phase产出写入staging文件(持久化) | Handoff Note结构化(对齐压缩模板)

### G3: 主动/compact策略 (优于等待自动触发)

> **Ch9启示**: 带自定义指令的主动`/compact`比被动自动压缩效果好——你能指定保留什么。

**何时主动/compact**:
1. Phase完成后、下一Phase开始前 — 释放空间，保留关键结论
2. 大量Agent并行返回后 — staging已commit，工具结果可压缩
3. 感觉context压力上升时 — 不等到自动触发(那时可能丢失更多)

**主动/compact最佳实践**:
```
/compact 重点保留: ①当前研究的核心矛盾和主线thesis ②每Phase的关键结论和未解决问题
③被否决的方案及原因 ④Kill Switch条件 ⑤下一步行动计划。代码片段要完整保留。
```

### G4: Handoff Note对齐压缩9段模板

> **Ch9启示**: 压缩摘要按9段结构组织。Handoff Note对齐这个结构=压缩时信息保留率最高。

**Handoff Note标准结构** (对齐压缩模板 + 稳定性标记):
```markdown
## Handoff Note — {TICKER} Phase {N} → Phase {N+1}

### 1. [SESSION] 主要请求与意图
当前研究目标 + 用户的显式要求
⚠️ 压缩后必须保留: 这是恢复context的第一入口

### 2. [SESSION] 核心矛盾 + Thesis + 变量
核心矛盾 + 主线thesis + 关键变量 + Kill Switch
⚠️ 压缩后必须保留: 跨Phase推理链的锚点

### 3. [REFRESH] 文件清单 + 关键数据
文件路径 + 关键数据点(完整，非摘要)
⚠️ 这些文件在下个session必须重新Read, NEVER使用旧context中的版本

### 4. [SESSION] 已解决的问题 + 被否决方案
Phase中遇到的问题 + 如何修复 + 被否决的方案及原因
⚠️ 高丢失风险: 压缩模板侧重"做了什么", "为什么不做X"最容易被压没

### 5. [SESSION] 用户反馈记录
用户在本Phase中的所有关键指令/偏好/纠正
⚠️ 高丢失风险: 早期偏好多次压缩后消失

### 6. [SESSION] 待办任务
未完成的分析 + 需要验证的假设

### 7. [REFRESH] 当前精确状态
最后在做什么 + checkpoint.yaml状态 + 完成度数字

### 8. [SESSION] 下一步唯一优先
下一Phase的第一个动作 + 不要重复的事
```

### G6: 紧急保存 (保留原规则)

**Agent必须在以下时机主动执行 `bash scripts/context_save.sh`**:
1. **用户说context不够/要clear** — 立即执行，不问问题
2. **并行Agent全部返回后** — 立即commit staging产出，不等Phase完成
3. **任何阶段性产出完成时** — 报告/staging/data有变化就commit，不积压
4. **Phase完成时** — 每个Phase结束必须保存，不积压到下一Phase

**禁止**: 让用户手动提醒保存 | 未提交就建议/clear | 积压超过2个Agent产出不commit

### G7: 恢复预算感知 (Ch10, 5个硬约束)

> **Ch10核心**: 压缩后恢复不是"全部找回"，而是**预算分配问题**。理解预算才能影响恢复结果。

**五层恢复预算** (硬编码，不可修改):
| 预算项 | 限额 | 含义 |
|--------|------|------|
| 文件数量 | **5个** | 只恢复最近读取的5个文件(按时间戳排序) |
| 单文件上限 | **5K tokens** | 约2000-2500行代码，超长文件只保留开头 |
| 文件总预算 | **50K tokens** | 5个文件总量上限 |
| 单Skill上限 | **5K tokens** | Skill截断保留头部(关键指令) |
| Skill总预算 | **25K tokens** | 约5个Skill |

**免疫压缩的通道** (不受上述预算限制):
- **CLAUDE.md** — 通过系统提示词注入，永远存在
- **Plan附件** — 独立恢复通道，不占50K文件预算
- **Delta重播** — 工具声明/Agent列表/MCP指令完整重播

### G7.5: 信息稳定性分类 (Ch5缓存架构映射, v5.1新增)

> **源自**: Claude Code Ch5 systemPromptSection vs DANGEROUS_uncachedSystemPromptSection
> **核心**: 不是所有信息都一样稳定。显式分类→压缩时知道保留什么、丢弃什么、必须刷新什么。

**三级稳定性分类**:

| 级别 | 标记 | 含义 | 保鲜期 | 等价物 | 示例 |
|------|------|------|--------|--------|------|
| **CACHED** | `[STABLE]` | 整个会话不变, 压缩后无需重新获取 | 会话级 | systemPromptSection | CLAUDE.md, 铁律规则文件, L0/L1原则, 质量门控阈值 |
| **SESSION** | `[SESSION]` | 会话内可能变化, Phase切换时应刷新 | Phase级 | 动态区段落 | thesis/主线, Kill Switch, Phase进度, staging摘要 |
| **VOLATILE** | `[REFRESH]` | 每次使用前必须重新读取, NEVER使用缓存版本 | 单轮级 | DANGEROUS_uncached | checkpoint.yaml, MCP财务数据, 当前股价, staging完整内容 |

**为什么需要这个分类**:
- 压缩后AI重新读取刚读过的文件(G10信号) → 如果是[STABLE]文件, 不需要重读(浪费恢复名额)
- 压缩后AI用旧staging数据继续写 → 如果staging标记了[REFRESH], 会被提醒先重读
- Phase切换时AI忘记上一Phase的thesis → [SESSION]标记提醒在handoff中持久化

**文件稳定性清单** (投资大师框架):

```
[STABLE] — 压缩后不需要重读, CLAUDE.md免疫压缩自动保证:
  CLAUDE.md                          ← 系统提示词注入, 永远存在
  .claude/rules/*.md                 ← 铁律规则, 会话内不变
  knowledge/analysis_modules/*.md    ← 分析模板, 会话内不变
  knowledge/industry_modules/*.md    ← 行业模块, 会话内不变

[SESSION] — Phase切换时写入handoff持久化, 压缩后从handoff恢复:
  当前thesis + 核心矛盾              ← 写入handoff §2 "关键技术概念"
  Kill Switch条件                    ← 写入handoff §2
  被否决方案+原因                    ← 写入handoff §4 (G2高丢失风险#1)
  用户本session偏好/纠正             ← 写入handoff §5 (G2高丢失风险#2)
  Phase进度+完成状态                 ← 写入handoff §7
  Python估值结果(精确数字)           ← 写入data/文件 (G2高丢失风险#3)

[REFRESH] — NEVER使用context中的旧版本, 每次使用前必须重新Read:
  staging/{TICKER}_*.md              ← 内容随Phase推进变化
  data/checkpoint.yaml               ← 当前状态, 随时更新
  reports/{TICKER}/*.md              ← 组装中内容持续变化
  MCP工具返回的财务数据               ← 市场数据每日变化
  evolution_log.yaml                 ← 可能有新条目
```

**Agent行为规则**:
1. **压缩后恢复时**: 先读[SESSION]级的handoff note(含thesis/Kill Switch/进度), NEVER假设还记得
2. **Phase切换时**: [SESSION]级信息全部写入handoff, 不依赖context存活
3. **使用staging/data文件时**: [REFRESH]级文件必须先Read再使用, NEVER引用context中的旧内容
4. **[STABLE]文件不浪费恢复名额**: 压缩后如果需要铁律规则, 按需加载即可(CLAUDE.md免疫压缩), 不占G7的5个文件名额
5. **刷新时间戳优先给[REFRESH]文件**: 感觉压缩即将触发时, 刷新staging/checkpoint的时间戳(G8策略), 不刷新[STABLE]文件

**与G2/G7/G8的关系**: G7.5是G2(什么容易丢)+G7(恢复预算)+G8(时间戳策略)的**上游分类系统** — 先分类稳定性, 再决定保存/恢复/刷新策略。

### G8: 文件读取策略 (利用时间戳排序)

> **Ch10启示**: 恢复按"最近读取时间"排序，最近读的文件优先恢复。

**策略**:
1. **读你即将编辑的文件** — 优先读下一步需要的文件，不提前读所有参考文件
2. **刷新时间戳** — 如果感觉压缩即将触发，重新`Read`关键文件(staging/checkpoint)以刷新时间戳
3. **避免频繁切换** — 在5个文件间反复切换=浪费恢复名额。聚焦当前Phase的2-3个核心文件
4. **大文件截断预期** — 超过5K token的文件只保留开头部分。关键信息放在文件前部

### G9: Skill文件结构优化 (头部优先 + 发现描述精简)

> **Ch10启示**: Skill截断保留头部5K token。"技能文件开头的指令通常是关键部分"。
> **Ch15补充**: Skill列表仅占1%上下文窗口(~8K字符)，每条描述≤250字符。列表仅用于发现——完整内容在invoke时加载。

**SKILL.md写作原则**:
1. **关键指令放前500行** — 核心行为规则、触发条件、禁止事项必须在文件前部
2. **补充参考放后部** — 示例、历史参考、可选扩展放在后面(截断时牺牲)
3. **不依赖尾部内容** — 假设Skill的后半部分在压缩后不存在，前半部分仍能独立工作
4. **Skill描述精简** — SKILL.md的description字段≤250字符，只写触发条件——完整内容在调用时加载

### G11: 多次压缩累积效应

> **Ch10警告**: 超长会话经历多次压缩，信息密度递减不可逆。

**规则**:
- **Tier 3研究**: 每Phase一个session(2-3 Phase/session上限)，不试图单session完成全部
- **关键节点主动/compact**: 附自定义指令明确保留重点 > 被动等待自动压缩

### G12: 微压缩感知 (Ch11, 工具结果的隐性清除)

> **Ch11核心**: 微压缩不调用LLM，直接删除旧工具结果。三层机制独立运行，Agent必须理解工具结果的生命周期。

**三层微压缩机制**:
| 层 | 触发条件 | 行为 | 缓存影响 |
|---|---------|------|---------|
| 时间触发 | 离开>60分钟回来 | 清除旧工具结果，只保留最近5个 | 破坏缓存(缓存已过期) |
| 缓存微压缩 | 可压缩工具数超阈值 | 服务端cache_edits删除 | 保持缓存 |
| API声明式 | input_tokens>180K | 自动清除旧工具结果/使用 | API管理 |

**可压缩工具** (这些工具的结果会被清除):
- **结果可清除**: Read / Bash / Grep / Glob / WebSearch / WebFetch
- **使用可清除**: Edit / Write / NotebookEdit
- **不可压缩**: ToolSearch / SendMessage / Agent等

**keepRecent=5规则**: 微压缩后只保留最近5个工具结果。第6个及更早的Read/Grep/Bash结果会被替换为`[Old tool result content cleared]`。

**Agent行为规则**:
1. **聚焦工具调用**: 不散射式Read 10个文件——只有最近5个的结果会存活
2. **关键数据立即持久化**: 工具返回的关键数据(财务数字/估值结果)立即写入staging文件，不依赖工具结果在context中存活
3. **长时间中断后的预期**: 离开>1小时回来，大部分旧工具结果已被清除。正常操作=重新Read关键文件
4. **精准搜索**: 精确的Grep/Glob查询 > 宽泛搜索。减少单次工具输出大小(并行工具调用受200K字符消息预算限制)

### G13: 工具结果生命周期管理 (Ch11衍生)

> **核心**: 工具结果不是永久的——理解其生命周期才能避免"数据消失"的困惑。

**工具结果的生命周期**:
```
工具调用 → 结果返回(在context中) → [微压缩: 第6个起被清除] → [自动压缩: 被摘要化] → [多次压缩: 信息递减]
```

**持久化策略** (按信息重要度):
| 重要度 | 信息类型 | 持久化方式 |
|--------|---------|-----------|
| **最高** | 研究约束/核心偏好 | 写入CLAUDE.md(免疫一切压缩) |
| **高** | Phase结论/Handoff | 写入staging文件(持久化到磁盘) |
| **高** | 估值计算结果 | 写入data/文件(Python输出) |
| **中** | 多步计划 | 用Plan模式(独立恢复通道) |
| **低** | 搜索/查询结果 | 不持久化，需要时重新执行 |

**禁止**: 在context中保留关键数据不写入文件 | 假设工具结果会一直存在 | 离开>1小时后依赖旧工具结果

**告知而非隐藏** (Ch26补充): 截断/压缩时必须透明:
- 数据截断时标注来源("完整数据见data/{file}")
- Phase间传递时附staging文件路径，不写"如前分析"
- 压缩后不确定的数据→重新查询而非猜测。**"我需要重新查"比"大约是X"诚实100倍**

### G14: Token预算感知 (Ch12, 三层预算防线)

> **Ch12核心**: Token预算是安全机制——高估代价是提前压缩(轻微损失)，低估代价是API失败(灾难性)。

**三层预算防线**:
| 层 | 阈值 | 触发行为 |
|---|------|---------|
| L1 单工具结果 | **50K字符** | 超限→存盘+仅显示2KB预览 |
| L2 单消息聚合 | **200K字符** | 并行工具调用总量上限 |
| L3 上下文窗口 | 精确usage+粗估 | 驱动自动压缩/微压缩 |

**Token密度差异** (影响预算消耗速度):
| 内容类型 | 字节/Token | 含义 |
|---------|----------|------|
| 普通代码/文本 | 4 | 100KB≈25K tokens |
| **JSON/JSONL** | **2** | **100KB≈50K tokens(2倍密度!)** |
| 图片/PDF | 固定2,000 | 不按base64长度计算 |

**Agent行为规则**:
1. **控制工具输出大小**: 精确搜索 > 宽泛搜索。用`Grep pattern --glob "*.py"`而非全局搜索
2. **JSON密度警觉**: FMP/MCP返回的JSON数据消耗2倍token。大JSON立即提取关键数据写入staging，不在context中保留完整JSON
3. **并行工具协调**: 4个并行工具各50K=200K上限。大规模并行搜索分多轮执行
4. **Read工具优势**: Read的输出**永不被持久化**(声明Infinity)，始终完整显示——用Read读关键文件最可靠
5. **粗略估算偏差预期**: token估算有±50%偏差，压缩触发时机可能偏早或偏晚，属正常行为

### G15: 缓存感知 (Ch13-Ch15, /clear vs /compact + Skill加载纪律 + 优化模式)

> **Ch13核心**: 每次API调用有~30K tokens固定开销(系统提示词11K+工具定义20K)。缓存命中可降90%成本。但前缀任何变化=缓存失效。
> **Ch14补充**: 90%的缓存中断是服务端原因(路由/驱逐)，不是客户端bug。Agent只需控制可控部分(10%)。
> **Ch15优化原则**: 越靠近API请求前端→越需要稳定。动态内容推后/降频/用附件。"宁可不说，不要说了又删"。

**Agent行为规则**:

1. **/compact优先于/clear**: /clear重置所有缓存锁存→下次API调用的30K固定开销无法利用缓存。/compact不重置锁存→缓存连续。**除非用户明确要求，优先建议/compact而非/clear**

2. **Skill加载=工具定义膨胀**: 每加载一个Skill→工具定义增大→缓存键更长→更脆弱。强化CLAUDE.md既有规则: **每Phase仅激活需要的3-5个skill，不预加载全部23+**

3. **MCP工具成本意识**: 我们的MCP工具(investment-master)使系统提示词缓存从global降级到org级别。MCP调用越多→缓存命中率可能越低。**批量MCP调用 > 散点MCP调用**

4. **Session稳定性**: 避免mid-session配置变化(切换模型/切换fast mode)。每次切换可能破坏50-70K tokens缓存

### G16: Ephemeral Injection (v5.1新增, Hermes Agent借鉴)

> **源自**: Hermes Agent prompt_builder.py — memory和plugin context只在API调用时注入user message，永不写入系统提示词或持久化messages列表。这保护了prompt cache prefix不被破坏。
> **核心**: 区分"持久消息"和"临时注入"，压缩时临时注入最先被清除。

**三级消息分类** (与G7.5稳定性分类互补):

| 级别 | 含义 | 压缩优先级 | 示例 |
|------|------|-----------|------|
| **PERSISTENT** | 持久消息——用户指令+关键分析结论+thesis | 最后压缩 | 用户显式指令、Phase结论、Kill Switch |
| **TOOL_RESULT** | 工具返回——有价值但可替代 | 中等，裁剪为一行摘要 | MCP财务数据、Bash输出、Grep结果 |
| **EPHEMERAL** | 临时注入——用完即可丢弃 | 最先压缩 | Skill全文、中间计算过程、重复搜索 |

**Agent行为规则**:
1. **MCP数据立即提取**: 工具返回的JSON立即提取关键数字写入staging，不依赖原始JSON在context中存活
2. **Skill内容用完释放**: Skill调用结果形成结论后，原始Skill输出可安全丢弃(结论已持久化)
3. **工具摘要替代全文**: 压缩时用`context_compress.sh`生成的一行摘要替代完整工具结果(Hermes tool pruning模式)
4. **PERSISTENT内容自包含**: 写入staging/handoff的结论必须自包含核心证据，不写"如前所述"

**与G7.5的关系**: G7.5的`[STABLE]/[SESSION]/[REFRESH]`分类是**文件级**稳定性(哪些文件需要重读)。G16的Ephemeral分类是**消息级**优先级(context中哪些消息先压缩)。两者互补，不冲突。

### G17: 主动压缩脚本 (v5.1新增, Hermes Agent借鉴)

> **源自**: Hermes Agent context_compressor.py — 在50%上下文窗口时主动触发压缩，而非等到83.5%被动触发。
> **核心**: 主动压缩比被动压缩信息保留率更高。

**脚本**: `bash scripts/context_compress.sh <TICKER>`

**触发时机**:
1. **Phase完成时**: `phase_complete.sh`已自动调用(v1.1, Step 4.5)
2. **Phase中期**: 写完大章节(≥30K字符)后主动调用
3. **感觉context压力上升时**: 不等自动触发

**产出**: `reports/{TICKER}/data/tool_execution_summary.md` — 所有工具操作的一行摘要，压缩后可用此文件恢复"做过什么"。

**与G3(/compact)的关系**: G17先生成摘要(保留信息)→再/compact(释放空间)。顺序不能反——先compact会丢失工具结果，之后无法生成摘要。

### 压缩友好的写作习惯

> **目标**: 让AI写的内容在被压缩时保留率最高

1. **结论前置**: 每段先写结论再展开——压缩时截断尾部不丢核心
2. **关键数字独立行**: 重要数字/阈值/Kill Switch条件用独立行+加粗——压缩模板要求"specific details like file names, full code snippets"
3. **否决记录显式化**: "不选X因为Y"比"选了Z"更容易在压缩中被保留——因为它同时出现在"决策"和"问题解决"两个段落中
4. **避免隐式引用**: 不写"如前所述"——压缩后"前述"已不存在。每个论点自包含核心证据
5. **Plan模式利用**: 多步任务用Plan制定计划——Plan有独立恢复通道，不受50K文件预算限制
