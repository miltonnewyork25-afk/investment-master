# 多步深度反思系统 v1.0

> **设计原理**: 单次反思 = 浅层结论。多步反思 = 每步聚焦一个维度，用足够推理深度产出可操作结论。
> **替代**: 原有单pass反思(autopsy→AI填入quality/technique/lesson)保留为Step 0机械测量，本系统在其上叠加3步结构化深度反思。
> **核心收益**: 行业模块复用(R1做一次) + 结构化缺口发现(R2) + 可验收评分(R3)

---

## 触发条件

| 场景 | 执行范围 |
|------|---------|
| **报告Complete后** | Step 0 → R1(首次) → R2 → R3 |
| **同行业第二份报告后** | Step 0 → R2 → R3 (复用R1) |
| **快速模式(只想知道缺什么)** | 仅R2的模板C部分 (~20分钟) |
| **v2重做前** | R2 → R3 (产出v2目录) |

## 前置步骤: Step 0 机械测量 (保留现有)

```bash
bash scripts/post_report_autopsy.sh {TICKER} {REPORT_FILE}
```

Step 0产出数据供R2/R3引用: 字符数、CG结果、DM锚点、Mermaid数、Scorecard分数。

## Step R1: 行业模块基建 (模板A)

> **时间**: 20-30分钟 | **频率**: 同行业只做一次 | **产出**: `knowledge/industry_modules/{industry}_modules.md`

### R1.1 目标

建立行业的MECE分析坐标系。不是描述某个公司，而是定义"分析这个行业的任何公司都必须覆盖的维度"。

### R1.2 执行提示词

```
请用MECE给出【{行业}】的10个核心分析模块(M1-M10)。

要求:
1. 模块划分必须满足MECE(互斥+穷尽)
2. 参考现有行业文档 docs/industry/{industry}_deep.md 的内容，但以模块化方式重组
3. 根据行业特性判断是否需要启用扩展模块E1-E5(最多5个)，说明触发理由

对每个模块输出:
- 模块名称 + 一句话定义
- 必问3问 (分析任何公司时必须回答的3个问题)
- 必填KPI 3个 (可量化、可跨公司对比)
- 1条数学一致性检验 (或交叉验证规则)
- 1条Kill Switch (阈值 + 触发动作)

不要写任何公司内容，只输出行业通用模板。
输出要可用于后续R2的目录映射与评分。
```

### R1.3 产出格式

```yaml
# {industry}_modules.md
# 行业分析模块模板 v1.0
# 生成日期: YYYY-MM-DD
# 适用公司示例: TICKER1, TICKER2, TICKER3

modules:
  M1:
    name: "[模块名]"
    definition: "[一句话定义]"
    questions:
      - Q1: "[必问问题1]"
      - Q2: "[必问问题2]"
      - Q3: "[必问问题3]"
    kpis:
      - KPI1: "[指标名] — [计算方式] — [行业基准范围]"
      - KPI2: "[指标名] — [计算方式] — [行业基准范围]"
      - KPI3: "[指标名] — [计算方式] — [行业基准范围]"
    consistency_check: "[数学一致性检验描述]"
    kill_switch:
      threshold: "[具体阈值]"
      action: "[触发时的动作]"

  M2:
    # ... (同上格式, M1-M10)

extensions:
  E1:
    name: "[扩展模块名]"
    trigger: "[启用条件]"
    # ... (同M格式)
```

### R1.4 质量检查

- [ ] 10个模块覆盖行业全部核心维度? (遗漏检查)
- [ ] 模块间无重叠? (MECE检查)
- [ ] 每个KPI有行业基准范围? (可对比检查)
- [ ] Kill Switch阈值具体可执行? (非"显著下降"等模糊表述)
- [ ] 与现有 `docs/industry/{industry}_deep.md` 兼容? (不矛盾)

### R1.5 与现有行业文档的关系

- `docs/industry/{industry}_deep.md` = **Phase执行指南** (怎么做分析)
- `knowledge/industry_modules/{industry}_modules.md` = **反思坐标系** (分析完后检查覆盖了什么)
- 两者互补，不替代。R1可以从deep.md提取内容，但重组为模块化结构。

## Step R2: 深度报告审计 (模板B+C合并)

> **时间**: 40-60分钟 | **频率**: 每份报告 | **产出**: `reports/{TICKER}/reflection/deep_audit.md`
> **前置**: R1已完成(有行业模块模板)

### R2.1 目标

把报告放进模块坐标系，找出"误判点"和"结构缺口"。这是整个反思系统最核心的步骤。

### R2.2 执行步骤

**Part 1: 公司模块定位 (模板B)**

```
基于行业模块模板 knowledge/industry_modules/{industry}_modules.md，
请对【{TICKER}】逐模块定位(M1-M10 + 启用的扩展模块)。

每模块输出:
1. 公司当前状态 (一句话总结)
2. 与2-3个核心同业对比的差异 (只保留最关键2点)
3. 最可能被误判的点 (1-2条)
4. 需要补的证据字段 (列字段名，不要展开长文)
5. 对应的Kill Switch状态 (是否已触发/接近触发)

要求: 不允许泛泛叙事，所有结论必须对应字段。
```

**Part 2: 报告结构映射 (模板C)**

```
读取报告目录: {REPORT_FILE}
读取模块模板: knowledge/industry_modules/{industry}_modules.md

把报告目录逐条映射到模块(M1-M10 + 扩展模块)。输出:

1. 缺失模块 — 目录层面缺专章或覆盖明显不足的模块
2. 重复章节 — 同一问题被多次讲(列出具体章节号)与合并建议
3. 叙事但缺验证的章节 — 缺字段/缺一致性检验/缺Kill Switch
4. 建议删减或下沉附录的部分 — 理由: 不影响结论/不可验证/重复

最后给一个"最短补齐路线图":
只补3个模块就能显著升维(含每个模块最小字段表 + 一致性检验 + Kill Switch)。
```

### R2.3 产出格式

```markdown
# {TICKER} 深度报告审计
# 审计日期: YYYY-MM-DD
# 报告版本: {REPORT_FILE}
# 行业模块: {industry}_modules.md

## Part 1: 模块定位矩阵

| 模块 | 公司状态 | 同业差异 | 误判风险 | 证据缺口 | KS状态 |
|------|---------|---------|---------|---------|--------|
| M1   | ...     | ...     | ...     | ...     | ...    |
| ...  |         |         |         |         |        |

## Part 2: 报告结构映射

### 缺失模块
| 模块 | 缺失程度 | 影响(对结论的影响) |
|------|:--------:|------------------|
| ...  | 完全缺失/不足 | ...         |

### 重复章节
| 问题 | 出现章节 | 合并建议 |
|------|---------|---------|
| ...  | Ch3, Ch12, Ch18 | 保留Ch3, Ch12/18合并 |

### 叙事缺验证
| 章节 | 缺什么 | 补救成本(高/中/低) |
|------|--------|:-----------------:|
| ...  | 缺KPI, 缺KS | 中 |

### 删减/下沉建议
| 章节 | 建议 | 理由 |
|------|------|------|
| ...  | 下沉附录 | 不影响结论 |

## Part 3: 最短补齐路线图 (Top 3模块)

### 补齐模块1: {MODULE_NAME}
- 最小字段表: [3-6个字段]
- 一致性检验: [具体公式/交叉验证]
- Kill Switch: [阈值 + 动作]
- 预估工作量: [字符数 + 数据来源]

### 补齐模块2: ...
### 补齐模块3: ...
```

## Step R3: 评分 + 升级路线 (模板D+E合并)

> **时间**: 20-30分钟 | **频率**: 每份报告(可选) | **产出**: `reports/{TICKER}/reflection/upgrade_roadmap.md`
> **前置**: R2已完成

### R3.1 目标

把R2的定性审计转化为量化评分 + 可执行的补证据任务单。如果计划v2重做，同时输出v2目录。

### R3.2 执行步骤

**Part 1: 模块门控评分 (模板D)**

```
基于R2审计结果，按0-2分给每个模块评分:
  0分 = 纯叙事(无指标、无验证、无Kill Switch)
  1分 = 有指标但缺一致性检验或Kill Switch
  2分 = 可验证 + 有一致性检验 + 有Kill Switch

输出:
1. 各模块评分 + 扣分原因(缺哪3个字段/哪条检验)
2. 总分: X / {模块数*2} (百分比)
3. Top 10补证据任务清单(按影响度排序)
   - 每个任务: 字段名 + 数据来源类型 + 预估工作量
4. 发布门槛建议: 当前是否达到可发布标准

要求: 任务必须可执行(字段+来源类型)，不写空话。
```

**Part 2: v2目录收敛 (模板E, 仅v2重做时)**

```
基于模块映射与最短补齐路线图，请输出【{TICKER} v2最终目录】:

每章包含:
- 章节名
- 对应模块(M1-M10/E1-E5)
- 合并/删减说明(相比v1变化)
- 每章最小字段表(3-6个)
- 每章1条一致性检验 + 1条Kill Switch

要求: 主文只保留可验证内容，方法论下沉附录。
```

### R3.3 产出格式

```markdown
# {TICKER} 升级路线图
# 日期: YYYY-MM-DD
# R2审计: reports/{TICKER}/reflection/deep_audit.md

| M3   | 0    | 纯叙事, 无KPI |
| ...  |      |         |

**总分**: X / Y (Z%)
**发布门槛**: >= 80%模块达到2分 → 当前{PASS/FAIL}

## Top 10 补证据任务清单

| # | 任务 | 模块 | 字段 | 数据来源 | 工作量 | 影响度 |
|---|------|------|------|---------|:------:|:-----:|

|---|--------|------|--------|-----------|-----------|------------|

| 2 | ...    | M2+M3 | 合并  | F1-F5     | ...       | ...        |
```

## 与现有系统的集成

### 进化循环更新

```
报告Complete
    |
    v
Step 0: post_report_autopsy.sh (机械测量, 5分钟)
    |
    v
Step R1: 行业模块基建 (首次20分钟, 后续复用)
    |
    v
Step R2: 深度报告审计 (40-60分钟, 核心价值步骤)
    |
    v
Step R3: 评分+升级路线 (20-30分钟, 可选)
    |
    v
进化提议汇总 (从R2缺口+R3任务清单提取EVO-XXX)
    |
    v
用户审批 → evolution_log.yaml → 下份报告受益
```

### 与find_relevant_knowledge.sh的集成

下份报告Phase -1时，`find_relevant_knowledge.sh` 应检查:
1. 行业模块模板是否存在 → 存在则跳过R1
2. 同行业上份报告的deep_audit.md → 提取未修复的缺口作为本次警告

### 与excellence_catalog的关系

- R2的"误判点"可能产生新的冠军候选(发现独特分析视角)
- R3的"评分矩阵"为excellence_catalog的技术评分提供结构化依据
- 两者互补: excellence_catalog记录"什么做得好"，deep_audit记录"什么还缺"
