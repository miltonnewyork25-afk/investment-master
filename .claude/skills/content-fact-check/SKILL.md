# Content Fact-Check v1.0 — 事实保真门控

> **设计原因**: RCL文章将"母公司注册在利比里亚"压缩成了"船注册在巴哈马"——研报6处正确，文章1处错误。事实错误是唯一能摧毁信任的东西（Mayer ABI模型：Integrity=0则Trust=0）。
>
> **定位**: Content Engine写作流水线的Layer 3.5，在品味Agent之后、E轨合规检查之前执行。

---

## 触发条件

文章初稿（或修改稿）完成后，发布前必须执行。无例外。

---

## 执行流程

### Step 1: 提取事实断言

从文章中提取所有可验证的事实性断言，分为5类：

| 类别 | 示例 | 风险等级 |
|------|------|---------|
| **实体属性** | 注册地、总部、CEO姓名、品牌归属 | 最高 — 错了就是硬伤 |
| **财务数字** | 收入、利润、市盈率、税率、回购金额 | 高 — 数字错误损毁专业性 |
| **时间/事件** | "2018年买入"、"去年感恩节"、"八个季度连续净卖出" | 中 — 时间线错误影响叙事可信度 |
| **比较/排名** | "全球第二大"、"三家最低"、"历史最佳" | 中 — 相对关系错误暴露粗糙 |
| **因果/机制** | "Section 883豁免"、"巴哈马旗=无最低工资" | 高 — 机制错误比数字错误更致命 |

**输出格式**:
```
[F-01] 实体属性: "皇家加勒比的母公司注册在利比里亚" → 待验证
[F-02] 财务数字: "将近三十亿美元的利润，交了四千六百万的税" → 待验证
[F-03] 因果机制: "巴哈马旗=没有最低工资，没有工时上限" → 待验证
...
```

### Step 2: 定位源报告

确定文章对应的源报告路径:
```bash
# 从文章内容推断TICKER
# 查找对应报告
bash scripts/find_best_reference.sh {TICKER}
```

如果文章引用了多份报告（跨报告连接文章），逐一定位。

### Step 3: 逐条交叉验证

对每条事实断言，在源报告中搜索对应内容:

```
[F-01] ✅ PASS — 报告第88行: "公司注册于利比里亚" | 文章: "注册在利比里亚" | 一致
[F-02] ✅ PASS — 报告DM-P2-015: "FY2024 Net Income $2,877M, tax $46M" | 文章: "三十亿/四千六百万" | 近似一致(人话化)
[F-03] ⚠️ WARN — 报告第1484行说"利比里亚公司法"治理宽松，但没有直接说"巴哈马旗=无最低工资" | 需要确认来源
[F-04] ❌ FAIL — 报告说"注册于利比里亚"，文章说"注册在巴哈马" | 事实变形!
```

### Step 4: 输出验证报告

```
## 事实保真验证报告
文章: {文件名}
源报告: {报告路径}
验证时间: {日期}

### 结果汇总
- 总断言数: X
- ✅ PASS: X
- ⚠️ WARN: X (需补充来源或确认)
- ❌ FAIL: X (必须修正)

### FAIL详情
[F-XX] 文章原文: "..."
       报告原文: "..."
       错误类型: 实体属性混淆 / 数字错误 / 因果链断裂 / ...
       修正建议: "..."

### WARN详情
[F-XX] 文章原文: "..."
       问题: 报告中无直接对应，可能来自外部来源
       建议: 补充来源 或 标记为推断
```

## 高风险模式 (从RCL错误归纳)

以下压缩模式最容易导致事实变形，验证时重点关注:

| 压缩模式 | 风险 | RCL案例 |
|----------|------|---------|
| **两个相似概念合并** | 混淆 | 注册地(利比里亚) + 船旗国(巴哈马) → 错误合并为"注册在巴哈马" |
| **数字人话化** | 精度丢失 | "$2,877M" → "三十亿" ✅可接受 / "$46M" → "五千万" ❌不可接受 |
| **因果链缩短** | 归因错误 | "Section 883豁免航运收入" → "注册在海外所以不交税" — 机制被简化 |
| **时间线压缩** | 顺序错误 | "2018买入→2020扛过COVID→2026卖出" — 确认每个时间节点 |
| **比较对象替换** | 张冠李戴 | "CCL注册在巴拿马/百慕大" 错误嫁接到RCL |

---

## 门控规则

- **有❌ FAIL → 必须修正后才能进入E轨合规检查**
- **有⚠️ WARN → 写作者决定：补来源 或 删除该断言**
- **全✅ PASS → 进入下一步**

---

## 在Content Engine流水线中的位置

```
Layer 3: 初稿写作 (E+P交汇)
    ↓
品味Agent审读 (T1-T9)
    ↓
写作者修改
    ↓
★ content-fact-check ★  ← 这里
    ↓
Layer 4: E轨合规检查 (E-01~E-13)
    ↓
Layer 5: 平台适配
    ↓
终稿
```

**为什么在品味Agent之后**: 品味修改可能改变事实表述（压缩、换措辞），所以在最终文本上做事实验证。

